Cairn V3.5 Draft · 2026-05-24

复杂 Markdown 渲染 + 红蓝对抗审查

本规格把“看得懂复杂报告”和“降低幻觉进入黑板”拆成两个可验收能力：安全 Markdown renderer 负责表达，红蓝 review gate 负责证据约束。

核心判断

Markdown

从轻量 parser 升级为安全渲染能力

支持 GFM 表格、任务列表、代码块、链接策略、Raw/Debug 与 XSS 测试，而不是继续手写越来越复杂的字符串替换。

Red Team

红队不是真理机器

它只能暴露证据缺口、反证和过度推断，减少 unsupported conclusion 被采纳的概率，不能保证完全无幻觉。

Architecture

不新增 Claim 图层

候选结论与 review 细节进入 ExecutionEvent / Artifact；采纳后的用户可见结果仍是 Fact。

红蓝审查流

Blue run

探索并产出 candidate fact、证据引用、不确定性。

Review gate

策略判断是否需要红队：off / targeted / required。

Red run

检查证据、反证、未证推断、复现风险。

Verdict

pass / revise / fail / needs_human。

Accept or block

通过才写 Fact；否则修订、人工确认或拒绝。

Architecture Delta

Intent / Branch -> ExecutionRun -> ExecutionEvent -> Artifact / EvidenceLink -> Fact 主链路不变。

新增的是 conclude 前的可选 Review Gate：蓝队候选先作为 event/artifact 保存，红队 verdict 也是 event/artifact，只有被采纳后才投影为 Fact。

需要避免的误区

不要把红队输出拆成一堆 Fact

那会污染用户心智图。红队 critique 默认是审查产物，不是新的业务结论。

不要恢复旧 transcript 路径

Output/Conversation/Review 仍必须消费 ExecutionEvent 和 Artifact，不走 /questions 或 /runs/*/transcript。

不要默认全量强审查

推荐默认 targeted，否则成本和延迟会让简单任务也变重。

验收口径

安全

Markdown XSS fixture 不执行脚本，危险协议不生成链接，外链带 noopener。

可审计

蓝队候选、红队 verdict、人工 override 都能刷新后追溯。

可门控

revise/fail/needs_human 不应静默写 Fact；pass 才可自动采纳。

待确认决策

  • 默认 review mode 是否采用 targeted？
  • 是否扩展 ExecutionTaskType=review，还是首版复用 conclude metadata？
  • 红队是否必须不同 worker/model，还是允许同 worker 独立 session？
  • Markdown 升级是否先在单文件 UI 中做，还是并入 v3.3 前端模块化？
