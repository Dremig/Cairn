# V3.5 Markdown Rendering and Red/Blue Review Requirements

日期：2026-05-24
状态：需求草案
依据：用户要求“引入比较复杂的点”、补强 Markdown 渲染，并引入“红蓝对抗机制”以控制幻觉；当前分支 `feature/markdown-red-blue-review`；本轮读取 `docs/architecture/cairn-architecture-ssot.md`、`docs/specs/v3.2-live-conversation-thread-requirements.md`、`docs/specs/v3.3-frontend-refactor-requirements.md`、当前 `cairn/src/cairn/server/static/index.html` 与相关测试搜索结果。

## 1. 核心判断

本需求包含两个不同层级的复杂点：

1. **复杂 Markdown 渲染**：当前轻量浏览器内 renderer 只能覆盖标题、列表、引用、代码块、链接等基础语法，适合作为 smoke 修复；若 Cairn 要把 worker report、conversation、fact description、hint 和证据摘要长期作为知识工作台展示，就需要 production-grade Markdown/GFM 渲染、安全 sanitizer、代码块与表格能力、长输出性能策略和测试护栏。
2. **红蓝对抗机制**：它不是“消灭幻觉”的魔法开关，而是把“结论是否有证据支撑、是否存在反证、哪些推断不可靠”显式化，并作为 Fact 采纳前后的门控与标注机制。它控制幻觉的方式是提高证据约束和审计可见性，而不是保证模型永远正确。

架构取舍：

- 不把红蓝机制做成新的 `Claim` 核心图层。除非未来明确需要长期逐条断言审核 workflow，否则候选结论、红队批注、蓝队修订、证据缺口应存入 `ExecutionEvent` / `Artifact`；被采纳后的用户可见结果仍是 `Fact`。
- `Fact` 可展示 review verdict、confidence、uncertainty、evidence sufficiency 等摘要元数据，但不承载 worker lease、heartbeat、cancel/retry 或完整审查日志。
- 红蓝机制应可配置、可按 intent/project/risk level 启用；不应默认强制所有小任务走昂贵审查。

## 2. 背景与现状

### 2.1 当前 Markdown 现状

当前 UI 是单文件 Alpine 前端，已新增轻量 `renderMarkdown(text)` / `renderMarkdownInline(text)`：

- 先 escape HTML，再生成有限 HTML，避免直接执行原始 HTML。
- 支持 heading、paragraph、ordered/unordered list、blockquote、fenced code、inline code、bold/italic、link、horizontal rule。
- 已应用到 fact/intent description、conversation event text、hint content 等位置。

它的限制：

- 不是完整 CommonMark/GFM parser，复杂嵌套、表格、task list、代码语言标记、自动链接、脚注、数学公式等都不稳定。
- sanitizer 与 renderer 绑在手写逻辑中，可维护性和安全审计性较弱。
- 缺少大文本、恶意输入、XSS payload、链接协议、图片/附件策略、copy code、anchor heading 等系统测试。
- 若后续按 v3.3 做前端模块化，该能力应变成独立 Markdown rendering service/component，而不是继续堆在 `index.html` 的全局方法里。

### 2.2 当前结论采纳现状

SSOT 当前规定主链路为：

```text
Intent / Branch
  -> ExecutionRun
  -> ExecutionEvent
  -> Artifact / EvidenceLink
  -> Fact projection when concluded
```

当前产品心智模型仍是 `Fact/Intent DAG`：

- `Intent` 是工作订单。
- `ExecutionRun` 是一次实际运行。
- `ExecutionEvent` 是实时 output/conversation/tool stream 的事实源。
- `Artifact` / `EvidenceLink` 保存证据。
- `Fact` 是进入黑板的探索结果节点，不是 atomic assertion。

因此红蓝机制应嵌入 execution/review/conclude 流程，而不是恢复旧 `/questions`、`/runs/*/transcript` 或新增与 SSOT 冲突的事实源。

## 3. 目标

### 3.1 Markdown 目标

1. 将 Markdown 渲染从“临时轻量 parser”升级为可维护、安全、可测试的渲染能力。
2. 支持 worker 真实输出中常见复杂结构：GFM table、task list、嵌套 list、fenced code language、长代码块、链接、图片/附件占位、blockquote、多段报告。
3. 默认禁止或严格清洗 raw HTML，防止 XSS、javascript/data 协议、事件属性、style 注入和 tabnabbing。
4. 为 report/fact/conversation/hint 提供一致渲染体验，保留 Raw/Debug 入口。
5. 与 v3.3 前端重构方向兼容：渲染能力应能迁移到独立模块或构建产物，不继续扩大单文件隐式逻辑。

### 3.2 红蓝对抗目标

1. 在高风险或用户指定的探索中，让蓝队先产出候选结论与证据索引，让红队独立检查证据充分性、反证、未证推断、复现风险和不确定性。
2. 红队 review 结果必须作为可审计事件/产物保存，并可在 UI 中被用户查看。
3. 系统根据 review verdict 决定：自动采纳、要求蓝队修订、降级为低置信 Fact、标记需要人工确认，或不采纳。
4. 用户可以手动 override，但 override 必须留下审计事件和原因。
5. 控制幻觉的产品语义应明确：减少 unsupported conclusion 进入黑板的概率，并让风险可见；不承诺绝对正确。

## 4. 非目标

- 不引入 `Claim` 作为新的长期核心实体；本版不把 Fact 拆成 atomic claims。
- 不把红队输出直接当作反向 Fact 注入图中；红队结果默认是 review artifact/event，只有用户或蓝队后续探索采纳后才可能形成新的 Fact/Intent。
- 不恢复 `run_provenance`、`/runs/*/transcript`、`/questions`、`server/transcripts/*` 作为主链路。
- 不让前端解析 worker 私有 stdout JSON 来判断 review 语义；review 主路径必须来自标准 execution events/artifacts/API projection。
- 不强制所有项目、所有 intent 都使用红蓝审查；默认策略必须考虑成本和延迟。
- 不在本需求中指定最终前端框架；可以继续 Alpine，也可以在 v3.3 规划中选择 Vite/TypeScript/React/Vue/Svelte 等。

## 5. 用户流程

### 5.1 复杂 Markdown 阅读

1. 用户打开 project/fact/intent/conversation/report。
2. Markdown 内容以格式化形式展示：标题层级、表格、任务列表、代码块、链接和引用可读。
3. 代码块可横向滚动，保留语言标记；后续可增加 copy 按钮。
4. 外链默认新窗口打开并带 `noopener noreferrer`；危险协议不生成可点击链接。
5. 用户可在需要时切换 Raw/Debug，查看原始文本或渲染失败原因。

### 5.2 红蓝审查默认流

1. 用户创建项目或 intent 时，可选择 review mode：`off | targeted | required`。
2. 蓝队 execution 执行探索，产出候选结论、证据引用和不确定性说明。
3. 若策略命中，dispatcher/server 创建或调度 red review execution。
4. 红队读取蓝队 execution events、artifacts、evidence links 和相关 graph context，产出 review verdict：
   - `pass`：证据充分，可采纳。
   - `revise`：核心方向可能对，但存在证据缺口或表述过度，需要蓝队修订。
   - `fail`：结论不应采纳，存在重大反证、无证跳跃或不可复现。
   - `needs_human`：机器无法可靠裁决，需要用户确认。
5. 根据 verdict：
   - `pass`：系统可自动 conclude intent 并写入 Fact。
   - `revise`：蓝队得到红队 critique 后重写候选结论，再次 review 或转人工。
   - `fail`：不写入 Fact；intent 保持 open、withdrawn 或生成后续澄清 intent，取决于规划。
   - `needs_human`：UI 显示待确认状态，用户可 accept/reject/request revision。
6. 采纳后的 Fact detail 展示 review summary、confidence/uncertainty、证据链接和可展开审查记录。

### 5.3 人工 override

1. 用户看到红队 `fail` 或 `needs_human` 后，可选择人工采纳、人工驳回或要求继续探索。
2. override 必须填写或自动记录原因、操作者、时间、被 override 的 verdict。
3. override 不删除红队记录；UI 必须继续显示“此 Fact 经人工 override 采纳/驳回”。

## 6. 功能需求

### 6.1 Markdown 渲染需求

- 支持 CommonMark 基础语义和 GFM 常用扩展：table、strikethrough、task list、autolink、fenced code language。
- 默认禁用 raw HTML；若保留 raw HTML，必须经过 allowlist sanitizer，且默认配置不允许 script/style/iframe/event handlers。
- 链接策略：
  - 允许 `http:`、`https:`、相对路径或仓库 artifact 安全路径。
  - 禁止 `javascript:`、危险 `data:`、`vbscript:` 等协议。
  - 外链加 `target="_blank" rel="noopener noreferrer"`。
- 图片策略：
  - 首版可只渲染为附件/链接占位，不直接加载任意远程图片。
  - 若允许图片，必须限制协议、尺寸、懒加载和错误占位。
- 代码块策略：
  - 保留语言 class 供后续高亮。
  - 大代码块不应撑破布局。
  - 后续可增加 copy button，但不作为首版必须项。
- 性能策略：
  - 长 conversation/report 应避免每次 Alpine render 都全量重算。
  - 可使用 memoization、server-side pre-render cache 或 virtualized display，规划阶段决策。
- 测试：
  - XSS payload golden tests。
  - GFM fixture rendering tests。
  - 链接协议 sanitizer tests。
  - 浏览器 smoke：Fact/Conversation/Hint 中 Markdown 正常渲染且 Raw 可见。

### 6.2 红蓝 review 策略需求

系统应支持至少三种 review mode：

- `off`：保持现有 conclude 流程。
- `targeted`：仅对高风险 intent、低置信候选、无证据候选、用户手动标记或项目策略命中的任务启用。
- `required`：所有 exploration conclude 在采纳 Fact 前必须经过 review 或人工 override。

策略命中条件至少包含：

- 用户在 intent 上显式勾选 `requires_review`。
- 项目设置 `review_mode=required`。
- worker 输出 `confidence` 低或 `uncertainty` 高。
- 缺少 artifact/evidence link。
- 结论包含高风险类型，例如安全、金融、法律、生产破坏性操作建议、架构核心迁移、外部事实依赖。
- 用户手动请求 red review。

### 6.3 蓝队候选输出需求

蓝队候选结论应包含：

- candidate fact title / description。
- evidence references：关联 execution event、artifact、file、command output 或 URL/外部来源摘要。
- uncertainty：已知不确定性与未验证假设。
- scope：结论适用边界。
- reproduction notes：必要时给出如何复现或验证。

这些内容在进入黑板前应作为 execution event/artifact 保存，不直接成为 Fact。

### 6.4 红队审查输出需求

红队审查必须结构化输出：

- `verdict`: `pass | revise | fail | needs_human`。
- `confidence`: `high | medium | low` 或等价等级。
- `unsupported_points[]`: 未被证据支撑的关键点。
- `contradictions[]`: 发现的反证或冲突。
- `missing_evidence[]`: 缺失证据。
- `risk_notes[]`: 失败路径、边界条件、用户可能误解处。
- `suggested_revision`: 面向蓝队的修改建议。
- `evidence_checked[]`: 红队实际检查过的 artifact/event 引用。

红队输出保存为 `ExecutionEvent(event_type=review)` 或 review artifact。具体 event type 命名由 planning 决定，但必须仍属于 ExecutionEvent 主链路。

### 6.5 采纳与门控需求

- 自动采纳必须满足：候选结论结构合法、必要 artifact/evidence 存在、review policy 允许、red verdict 为 `pass` 或 review mode 为 `off`。
- `revise` 不应直接写 Fact；应触发蓝队修订 execution、保持 intent open，或进入人工确认。
- `fail` 默认不写 Fact；可留下审查 artifact 并在 intent detail 显示失败原因。
- `needs_human` 必须在 UI 中显著提示，不得静默采纳。
- 手动 conclude 仍可存在，但如果项目是 `required`，手动 conclude 应要求填写 override reason 或先运行 red review。
- 所有采纳路径都必须能追溯 producing execution 与 review execution/artifact。

### 6.6 UI 需求

- Project settings：显示并可修改 review mode、默认 review risk threshold。
- Intent create/edit：可指定 requires review / review profile。
- Intent detail：展示 review state：not required、pending、reviewing、passed、needs revision、failed、needs human、overridden。
- Fact detail：展示 review badge、confidence、uncertainty、evidence sufficiency、review summary。
- Output/Conversation：能查看蓝队候选、红队 critique、蓝队修订链路。
- Timeline：记录 review requested、review started、review verdict、override、fact accepted/rejected。
- Markdown：所有上述 review summary 与 evidence snippets 使用安全 Markdown 渲染。

## 7. 数据/API/界面需求

### 7.1 数据边界

首选边界：

- Project/Intent 可新增 review policy/config 字段或 metadata。
- ExecutionRun 可通过 `task_type` / `phase` / metadata 表达 review execution；若现有枚举不足，可扩展为 `review`，但需在 SSOT delta 和 migration 中明确。
- ExecutionEvent 承载 review lifecycle 与结构化 verdict。
- Artifact 保存完整 review report、candidate report、evidence bundle。
- EvidenceLink 可连接 accepted Fact 与 producing artifact、review artifact，relation 可表达 `supports`、`contradicts`、`derived_from`、`reviewed_by` 等；若当前 relation 不足，规划阶段决定扩展。
- Fact metadata 保存用户可见 review summary，不保存完整审查日志。

不应做：

- 不把红队 critique 写成多个小 Fact。
- 不让 Intent 持有 live review lease/heartbeat。
- 不新增与 ExecutionEvent 平行的 review log 事实源。

### 7.2 API 边界

规划阶段需定义或调整：

- Project settings API：review mode / threshold。
- Intent API：requires review / review profile。
- Dispatcher API：创建、lease、finish review execution 的契约。
- Conclude API：在 review mode 下的自动采纳、人工 override、revision request 行为。
- UI projection：graph/detail/timeline 中暴露 review state 与 review summary。

所有 Output/Conversation 展示仍必须使用 execution/events/branch 主路径，不新增旧 transcript 路径。

### 7.3 Worker/Dispatcher 边界

- Dispatcher 负责根据 policy 调度 blue run、red review run、blue revision run。
- Worker driver 只负责执行具体命令并标准化事件，不在本地私有日志中保存唯一 review 状态。
- Red worker 可以是同模型不同 prompt、不同模型、不同 provider 或同 worker 的独立 session；默认应尽量与 blue worker 隔离上下文，避免只是复述蓝队结论。
- Review prompt 必须要求引用证据，禁止只做风格性评价。
- 若 red worker 不可用，策略决定 fallback：等待、转人工、降级为 no-review，或阻止 conclude。

## 8. 关键决策点

1. **是否马上实施，还是先完成 v3.3 前端重构？** 复杂 Markdown 可以先在单文件 UI 中引入库和 sanitizer，但长期更适合跟 v3.3 模块化合并。
2. **review execution 是否扩展 `task_type=review`？** 如果扩展，需要 migration、API model、dispatcher selection、SSOT 更新；如果复用 `conclude` metadata，短期简单但语义较弱。
3. **review 默认策略是什么？** 推荐默认 `targeted`，避免成本和延迟压垮轻量任务。
4. **红队失败后 intent 状态如何表达？** 推荐不自动 withdraw；保留 open 并展示 review failed/revise state，除非用户选择放弃。
5. **EvidenceLink relation 是否扩展 `reviewed_by` / `contradicts`？** v3.2 已允许 supports/contradicts/derived_from 语义；若要让 UI 明确展示 review lineage，可能需要补充 relation enum 或 metadata。
6. **人工 override 的权限与审计粒度**：单用户本地系统可先记录 actor string；多用户后再接权限模型。
7. **Markdown library 选型**：若继续无构建，可用浏览器 bundle；若进入 v3.3，可选 `markdown-it`/`marked` + `DOMPurify` 或等价方案。要求是安全、可测、维护活跃，而不是特定库。

## 9. Proposed Architecture Delta

### 9.1 当前 SSOT 事实

- 当前主链路是 `Intent / Branch -> ExecutionRun -> ExecutionEvent -> Artifact / EvidenceLink -> Fact projection when concluded`。
- `Fact` 是进入黑板的探索结果节点，不是 atomic assertion。
- `Intent` 是工作订单，不承载 live runtime state。
- `ExecutionEvent` 是 Output、conversation transcript、tool/message stream 的唯一主数据源。
- `Artifact` 保存证据和大产物。
- 当前 `Pending Architecture Deltas` 暂无。

### 9.2 目标事实

在不改变 Fact/Intent/Execution/Artifact 基本边界的前提下，引入 **Review Gate** 作为 conclude 前后的可选审查层：

```text
Blue ExecutionRun
  -> candidate fact event/artifact + evidence links
  -> optional Red Review ExecutionRun
  -> review verdict event/artifact
  -> accept/revise/reject/human override decision
  -> Fact projection when accepted
```

目标约束：

- Review 是 execution-ledger 上的一类运行与事件，不是新的图本体。
- Candidate fact 在采纳前不是 Fact；它是 execution event/artifact 中的候选内容。
- Red review verdict 是 review event/artifact；采纳后只把摘要投影到 Fact metadata/UI。
- Conclude contract 必须能检查 review policy 与 verdict，必要时阻止或延迟 Fact 创建。
- UI Projection 必须暴露 review state，但不得从旧 transcript 或前端私有 parser 推断。

### 9.3 受影响 SSOT 章节

- §2 产品心智模型：补充 candidate/review 不改变 Fact 定义。
- §3 运行层主链路：补充 review execution/event/artifact 是 conclude gate 的组成部分。
- §5 Dispatcher / Server / Driver 边界：补充 dispatcher 调度 review，server 持久化 review policy/verdict，driver 标准化输出。
- §7 UI 投影规则：补充 review state 与 Markdown rendering 只消费标准 projection/events。
- §9 架构变更流程：实现完成后需把该 delta 合并进 SSOT 主体，并移除 Pending 标记。

### 9.4 行为不变项

- `Fact/Intent DAG` 仍是用户主工作面。
- 一个 successful concluded exploration intent 默认仍产出一个 primary result fact；区别是高风险场景下 successful concluded 可能需要先通过 review gate。
- Output/Conversation 主路径仍是 ExecutionRun/ExecutionEvent/Branch API。
- 旧 `/questions`、`/runs/*/transcript`、`run_provenance` 不恢复。

### 9.5 迁移/清理范围

- 新增 review policy/verdict 所需 schema/API/model/tests。
- 若扩展 execution task type 或 event type，需 migration 与 dispatcher/server contract tests。
- 旧轻量 Markdown renderer 可作为 fallback 过渡，但最终应被模块化 renderer/sanitizer 替换或包裹。
- 无需迁移旧项目为已 review；旧 Fact 默认显示 `review: not_available` 或等价状态。

### 9.6 Delta 生效条件

该 delta 只有在以下条件满足后才能合并进 SSOT 主体：

1. 需求经用户确认，并在 SSOT `Pending Architecture Deltas` 增加对应标记。
2. plan 明确 schema/API/dispatcher/UI/test 范围。
3. 实现通过 unit/API/dispatcher/UI smoke/manual E2E。
4. SSOT 主体更新为实际实现状态，并移除或归档 pending 标记。

## 10. 验收标准

### 10.1 Markdown 验收

- Fact、Intent、Hint、Conversation、Review summary 至少能安全渲染 heading、list、nested list、blockquote、fenced code、inline code、table、task list、link。
- XSS fixture 不执行脚本、不保留危险属性、不生成危险协议链接。
- 外链带 `target="_blank" rel="noopener noreferrer"`。
- Raw/Debug 入口仍可查看原始文本。
- 长 Markdown 不显著阻塞主界面；若无法完全保证，至少有明确性能上限与降级策略。
- 相关 unit/fixture tests 与浏览器 smoke 通过。

### 10.2 红蓝 review 验收

- Project/Intent 可以配置 review mode / requires review。
- 蓝队候选结论在采纳前能作为 event/artifact 查看。
- Red review execution 能读取蓝队证据并输出结构化 verdict。
- `pass` 可采纳为 Fact，并在 Fact detail 显示 review summary 与证据链接。
- `revise` 不直接写 Fact，能触发修订或等待人工。
- `fail` 不写 Fact，并展示失败原因。
- `needs_human` 在 UI 中阻塞自动采纳，用户 override 后留下审计记录。
- 所有 review lifecycle 进入 timeline/output，刷新后不丢失。
- 不调用旧 `/questions`、`/runs/*/transcript` 或 `run_provenance` 主路径。

### 10.3 回归验收

- 现有无 review 项目仍可按原流程 conclude。
- Dispatcher 在没有 red worker 或 Docker/worker 不可用时给出可理解错误，不静默写入未审查 Fact。
- Existing tests pass；新增 tests 覆盖 review policy、conclude gate、UI projection、Markdown sanitizer。
